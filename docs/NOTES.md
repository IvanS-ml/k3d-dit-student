# Журнал экспериментов

Все замеры на GPU, кроме лидерборда, сделаны на Kaggle (T4, sm_75). Студенты обучались на CPU (Mac, 4 потока).
Номера K3D-NN — ноутбуки Kaggle. В репозитории лежат те, что нужны для воспроизведения: `teacher/` (K3D-02) и `bench/` (K3D-11).

## Метрика (`scripts/hackathon/score.py`)
- На сэмпл: LPIPS (SqueezeNet) между рендерами мешей teacher и студента — 4 карты нормалей, 512 px.
- quality = 1 − LPIPS, если LPIPS ≤ 0.25, иначе 0. time = T_teacher / T_student (время `generate()`).
- Total = среднее quality × time. Упавший сэмпл даёт 0.
- T_teacher растёт с N почти линейно, а время маленького студента почти постоянно. Поэтому крупные объекты весят
  больше: объект на 40k вокселей — в ~4 раза больше медианного.
- В зачёт идёт только время `generate()`. Вход уже лежит на GPU. Между вызовами работают декодер и постобработка
  меша на CPU, поэтому кэши CPU и GPU перед каждым вызовом холодные.

## Цели (K3D-02) и зонд декодера (K3D-03)
- Цели посчитаны для всех 1208 объектов `train_part_001`, 0 ошибок:
  - x0c и x0u — одношаговые предсказания при t=1, с картинкой и без;
  - lat8 — 8 шагов, для 1127 объектов ≤ 20k вокселей.
- rel MSE(x0u, x0c): медиана 0.06 — картинка мало меняет одношаговое предсказание. x0c против lat8 — 0.31.

Зонд декодера: латенты-кандидаты прогнаны через официальный декодер и рендер, LPIPS к 50-шаговому эталону.

| Латент | LPIPS mean / max |
|---|---|
| x0u (1 шаг, только геометрия) | 0.055 / 0.099 |
| x0c (1 шаг, с картинкой) | 0.046 / 0.096 |
| среднее двух сидов teacher | 0.027 / 0.065 |
| эталон, сглаженный 3³ | 0.173 / 0.290, 4/16 за порогом |
| студент 256×2 → x0c | 0.092 / 0.136 |
| то же + подгонка разброса | 0.084 / 0.127 |
| студент 256×2 → lat8 | 0.096 / 0.139 |

Выводы:
1. Студент по одной геометрии работает.
2. MSE-цель подходит: усреднение сидов не вредит.
3. Сглаживать нельзя. Подгонка разброса помогает.
4. Цель x0c лучше lat8.
5. LPIPS студента растёт с N. На 20–37k вокселей он выходит на плато ~0.14 — до порога далеко.

## Размер и признаки студента (val rel MSE x0c, 119 объектов val)

| Прогон | Признаки | MLP | val |
|---|---|---|---|
| geo_ctx_big | occ + глубина эрозии + pos + ctx | 512×3 | 0.397 |
| x0c_h128_s60k | occ + pos + ctx | 128×2 | 0.429 |
| x0c_h64_s60k | occ + pos + ctx | 64×2 | 0.464 |
| geo_ctx_tok | + токен DINO | 256×2 | 0.570 (переобучение) |
| x0c_h128_noctx | occ + pos | 128×2 | 0.448 |
| x0c_h64_noctx | occ + pos | 64×2 | 0.481 |
| x0c_h48_noctx | occ + pos | 48×2 | 0.497 |
| x0c_h32_noctx | occ + pos | 32×2 | 0.524 |
| **x0c_h16_noctx (поставлен)** | occ + pos | 16×2 | **0.581** |

- ctx — число занятых вокселей в блоках 4³ вокруг вокселя. Он даёт −0.017 val, но дорог на инференсе — убран.
- Глубина эрозии почти ничего не даёт.
- Переобучения нет: на train-объектах ошибка та же, что на val.
- Грубое соответствие: +0.04 val ≈ +0.004–0.008 LPIPS.

Официальный путь на T4 (K3D-04, 16 объектов, `run_lat_dit_eval.py` + `score.py`, студент с ctx) дал Quality 0.9107.
На лидерборде на A100 у v4 H64 вышло 0.9076: оценка на T4 переносится.

## Движок: версии и находки

| Версия | Что изменилось | Находка |
|---|---|---|
| v1–v3 | CUDA-ядра через driver API, NVRTC/cubin, самопроверка, выбор режима | Веса из global-памяти внутри циклов: ~52 похода в L2 на тайл |
| v4 | Веса одним блобом в shared, активации в регистрах, без bbox | Вызов 64 / 76 мкс (тёплый / холодный); лидерборд 168k |
| v5 | `generate_impl` — один вызов C-расширения | Харнесс передаёт `vox_idxi` колонко-мажорным (npz в порядке Fortran) → быстрый путь откатывался |
| v6 | Ядра читают вход по страйдам, копии нет | В 1.75 раза быстрее v4 на T4, в 1.63 раза на A100; лидерборд 274k |
| v7 | Вдвое меньше инструкций на тайл, ровная раскладка тайлов, H16 | Лидерборд 303k (Quality 0.8951) |
| v8 | Ранний запуск пустого ядра и stamp (диагностика) | Не помогает |
| v9 | Выход из DLPack-слотов, запуск ядра до создания тензора | В цикле харнесса на T4 −39% (76.5 → 46.7 мкс) |

Разбор холодного вызова v7 H16 на T4 (K3D-10, метки rdtsc), мкс:

| Проверки входа | `new_empty` | Первый запуск ядра | Возврат + `synchronize` харнесса |
|---|---|---|---|
| 6 | 30 | 19 | 17–33 |

- Работа GPU в вызове — единицы микросекунд.
- После простоя GPU сбрасывает частоту, но постоянную часть это почти не меняет.
- Отсюда v9: выделение памяти обходит диспетчер и кэширующий аллокатор PyTorch, ядро запускается раньше.

## Воспроизводимость (проверено 2026-10-17)
- **Данные.** `prep_data.py` и `prep_train.py` из целей K3D-02 и входов `train_part_001` дают побайтно те же файлы
  (все memmap и все `train_*` / `val_*`), на которых учился поставленный студент. На 4 ядрах CPU это 37 с + 21 с.
- **Обучение.** Повтор `train_x0c.py` с `--seed 0` (два вызова по 140 с, 4 потока aarch64), против поставленного
  студента:

  | | повтор | поставленный |
  |---|---|---|
  | val rel MSE x0c | 0.5792 | 0.5805 |
  | то же после подгонки разброса | 0.7266 | 0.7292 |

  Выходы двух студентов различаются (rel MSE 0.17 друг к другу) — это другой локальный минимум того же качества.
- **Движок.** `engine/build.sh` с gcc 13.3, заголовками Python 3.11 и NVRTC 12.4.127 даёт побайтно те же `.so` и
  `.cubin`, что в `solution/weights`.
- **Сабмит.** `tools/make_submission.py` с параметрами по умолчанию даёт zip, файлы которого побайтно совпадают с
  отправленным `k3d_sub_v9_n16g.zip`.
- **Латенты.** `make_test_latents.py` на CPU x86_64 и aarch64: в 555 объектах (90.9 млн чисел) различаются 2 числа,
  на 1 ulp fp16 (≤ 5e-7).
- **`tests/test_pipeline.py`:**
  - признаки обучения и инференса совпадают бит в бит;
  - собранный сабмит повторяет обучающую модель (max rel diff ~1e-6);
  - обучение, разбитое на вызовы, совпадает с обучением за один вызов бит в бит.
